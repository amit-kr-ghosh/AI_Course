# AI / ML Masterclass

A compact GitHub workspace for the 14-day AI/ML Masterclass: foundations to modern AI engineering.

## Start here
1. Read `MASTER_COURSE_BLUEPRINT.md` for the governing curriculum and learning outcomes.
2. Read `COURSE_STATUS.md`, `SYLLABUS_TRACKER.md` and `PROGRESS_LOG.md` before teaching or continuing.
3. Review the latest relevant lesson, practical, project and assessment records in the three folders.
4. Resume from the last verified subtopic—not merely the next day number.

## Repository map
- `MASTER_COURSE_BLUEPRINT.md` — canonical 14-day curriculum, learning outcomes, mathematical depth, labs, deliverables, interview questions, assessments, projects, paper-reading framework and post-course roadmap.
- `COURSE_STATUS.md` — current checkpoint and next action.
- `SYLLABUS_TRACKER.md` — topic-level coverage and evidence across all 14 days.
- `PROGRESS_LOG.md` — chronological session history and handovers.
- `Lessons/` — daily explanations, derivations, examples and lesson checkpoints.
- `Practicals_Projects/` — notebooks, code, experiment results and nine portfolio projects.
- `Assessments/` — quizzes, milestone exams, interview practice and research-paper reviews.

## Operating rules
- The Master Course Blueprint is the authority for intended course content. Do not silently omit or replace its syllabus.
- The learner already knows Python; do not restart with beginner Python instruction.
- The course is planned as 14 days with a 150-minute target and flexible 120–180-minute daily commitment. A day may span multiple sessions; do not rush or force completion.
- Teach the problem, intuition, mathematics, architecture, implementation, evaluation and explanation as appropriate to the topic.
- Keep current-AI claims fresh and date-aware; verify current models, papers, libraries and APIs from primary sources when teaching those topics.
- Record only work actually completed and evidence actually reviewed. Distinguish introduced, practising, completed and demonstrated.
- Never invent scores, code execution, project outputs, paper findings, progress or GitHub commits.
- Use CPU-friendly or hosted alternatives when compute is unavailable; do not assume paid APIs, GPUs or cloud accounts.
- Protect secrets. Never ask for or commit tokens, passwords or private keys. Explain risks before destructive Git operations.

## Every session
Before: inspect status, tracker, progress log and relevant recent evidence. After: update notes, topic status, practical/project evidence, assessments and exact next checkpoint. Commit and verify repository updates when GitHub access is available; disclose any failure.

## Progress status vocabulary
Not started; Introduced; Practising; Completed; Demonstrated; Deferred. A discussion alone is not evidence of implementation or mastery.
