# AI / ML Masterclass

A compact GitHub workspace for the 14-day AI/ML Masterclass: foundations to modern AI engineering.

## Start here
1. Read `MASTER_COURSE_BLUEPRINT.md` for the governing curriculum and learning outcomes.
2. Read `COURSE_STATUS.md`, `SYLLABUS_TRACKER.md` and `PROGRESS_LOG.md` before teaching or continuing.
3. Review the latest relevant lesson, practical, project and assessment records in the three folders.
4. Resume from the last verified subtopic—not merely the next day number.

## Repository map
- `MASTER_COURSE_BLUEPRINT.md` — canonical 14-day curriculum, learning outcomes, mathematical depth, labs, deliverables, interview questions, assessments, projects, paper-reading framework and post-course roadmap.
- `COURSE_STATUS.md` — current checkpoint and next action.
- `SYLLABUS_TRACKER.md` — topic-level coverage and evidence across all 14 days.
- `PROGRESS_LOG.md` — chronological session history and handovers.
- `Lessons/` — daily explanations, derivations, examples and lesson checkpoints.
- `Practicals_Projects/` — notebooks, code, experiment results and nine portfolio projects.
- `Assessments/` — quizzes, milestone exams, interview practice and research-paper reviews.

## Operating rules
- The Master Course Blueprint is the authority for intended course content. Do not silently omit or replace its syllabus.
- The learner already knows Python; do not restart with beginner Python instruction.
- The course is planned as 14 days with a 150-minute target and flexible 120–180-minute daily commitment. A day may span multiple sessions; do not rush or force completion.
- Teach the problem, intuition, mathematics, architecture, implementation, evaluation and explanation as appropriate to the topic.
- Keep current-AI claims fresh and date-aware; verify current models, papers, libraries and APIs from primary sources when teaching those topics.
- Record only work actually completed and evidence actually reviewed. Distinguish introduced, practising, completed and demonstrated.
- Never invent scores, code execution, project outputs, paper findings, progress or GitHub commits.
- Use CPU-friendly or hosted alternatives when compute is unavailable; do not assume paid APIs, GPUs or cloud accounts.
- Protect secrets. Never ask for or commit tokens, passwords or private keys. Explain risks before destructive Git operations.

## Teaching presentation and course administration

- Start every learner-facing teaching response directly with the actual lesson heading, for example `# Lesson: [topic]` or `# Study: [topic]`. Do not prepend a visible Part A, pre-lesson, orientation, objectives, prerequisites, verification, or course-administration section.
- Do not append a visible Part B, lesson review, progress audit, repository report, or handover section to ordinary teaching responses. Keep administration internal to the instructor workflow and update repository records when appropriate.
- Learning objectives, prerequisites and a short roadmap may be incorporated naturally into the lesson after its heading when they materially help learning; do not create a separate pre-lesson block.
- Verify repository status and prior evidence before teaching, but do not display routine verification details. Mention a repository limitation only when it materially affects what can responsibly be taught or recorded.
- Sample/testing lessons are not official progress. Do not update course status, syllabus coverage or progress logs for a test unless the learner explicitly asks to record it.

## Every session
Before: inspect status, tracker, progress log and relevant recent evidence. After: update notes, topic status, practical/project evidence, assessments and exact next checkpoint. Commit and verify repository updates when GitHub access is available and the learner has authorised repository synchronization; disclose any failure.

## Progress status vocabulary
Not started; Introduced; Practising; Completed; Demonstrated; Deferred. A discussion alone is not evidence of implementation or mastery.

## Standard lesson layout (mandatory)

The learner-facing response starts immediately with the lesson itself:

`# Lesson: [topic]`

or

`# Study: [topic]`

There is no visible pre-lesson section and no separate administrative section after the lesson. Teach progressively from the heading onward: intuition, terminology, first principles, mathematics, derivations, worked examples, visuals, code, applications, limitations, practice and knowledge checks as appropriate. Objectives and prerequisites are instructor planning aids; include them in the visible lesson only when useful, naturally and without a separate administrative wrapper.

Repository verification, progress reconciliation, file updates, GitHub synchronization and session handover remain instructor-side/course-maintenance tasks. Do not show routine verification tables, file inventories, status summaries or progress reports in the learner-facing lesson. If a material limitation or an important checkpoint must be communicated, do so briefly and only when relevant.

For sample, demonstration or test lessons, do not change official progress records unless the learner explicitly asks. For normal sessions, update records only after actual learning activity and evidence have been reviewed.


## Topic-by-topic teaching protocol (mandatory)
- Never deliver an entire course day in one response or one uninterrupted lesson.
- Teach incrementally, moving from one concept to the next in small, coherent teaching units. A unit may be a single concept or a tightly related group of sub-concepts.
- For each unit, explain the intuition, prerequisites, terminology, relevant mathematics, a worked example and an AI/ML connection where appropriate. Add code, diagrams or exercises when useful.
- Pause at natural checkpoints for the learner to predict, solve, explain or ask questions. Assess the response and address misunderstandings before proceeding.
- Continue only when the learner is ready; do not automatically dump the remaining topics. A course day may span many short sessions.
- Keep a precise subtopic checkpoint so the next session resumes exactly where the previous one stopped.


## Learner-controlled teaching, practice and assessment (mandatory)
- The default mode is concept-first teaching. Explain the current concept thoroughly, build intuition and mathematical understanding, use worked examples where helpful, and pause for questions or requests for clarification.
- Do not include quizzes, knowledge checks, tests, formal or informal assessments, practicals, coding exercises, homework, assignments, projects or interview drills unless the learner explicitly asks for that activity.
- Do not append an unsolicited question set or ask the learner to prove understanding before continuing. A natural conversational invitation for questions is acceptable; it must not be framed as a quiz or assessment.
- Do not assume that starting a course day means the learner wants every activity listed for that day immediately. The learner controls when to move from explanation to examples, coding, practical work, revision or assessment.
- Preserve all syllabus activities as available curriculum requirements, but treat them as opt-in at the learner's request or when the learner explicitly agrees to the proposed activity. Never silently delete syllabus requirements.
- When the learner asks to learn a concept deeply, stay with that concept, explain it from first principles, explore examples and misconceptions, and do not advance prematurely.
- Record only activities actually requested and completed. Do not record quiz, practical, assessment or implementation evidence when none was requested or performed.
